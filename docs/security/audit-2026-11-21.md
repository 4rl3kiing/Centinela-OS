# Auditoría de seguridad y calidad — 2026-11-21

**Alcance:** rama `hardening/implementation-roadmap` (PR #1), commit base `e93c133`.
Unas 3 500 líneas de Rust (`kernel`, `hal`, `security`, `fuzz`), linker script,
configuración de Limine, scripts de construcción/arranque y los 4 workflows de CI.

**Método:** lectura completa del código, reproducción local de los fallos del CI,
pruebas unitarias nuevas para cada corrección y verificación de la cadena de
arranque en QEMU (BIOS y UEFI). Las correcciones están en el commit `16780c6`.

## Hallazgos de severidad alta

| ID | Componente | Problema | Corrección |
|----|------------|----------|------------|
| A1 | `security/permissions.rs` | `PagePermissions` tenía campos públicos: cualquier código podía construir una página W+X con un literal de struct y saltarse la invariante W^X. | Campos privados con accesores; `new` es el único constructor. `unmap_4k` rechaza describir una hoja W+X viva (`WriteExecuteMappingFound`). |
| A2 | `vmm.rs` `map_4k` | Tras escribir la hoja se invalidaba la TLB; si eso fallaba se devolvía error **con el mapeo ya visible**. El llamador podía reciclar el marco y dejar un alias vivo (use-after-free). | Se elimina esa invalidación: un cambio no presente → presente no requiere INVLPG (Intel SDM 3A §4.10.4.3, AMD APM 2 §5.5.2). |
| A3 | `tlb_shootdown.rs` | Si fallaba el envío de un IPI, las confirmaciones de los IPI ya entregados nunca se esperaban y podían satisfacer un shootdown posterior → traducciones obsoletas. | Se drenan las confirmaciones pendientes y se reporta solo lo no confirmado; el contrato exige confirmaciones con número de secuencia. |
| A4 | `main.rs` / linker | El rango físico del núcleo era la constante `0x100000`, pero Limine elige la dirección física. La reserva del PMM no protegía el núcleo real. | Petición *executable address* de Limine; el rango se valida contra las tablas de páginas activas en ambos extremos de la imagen. |
| A5 | `hal/cpu.rs` | Las escrituras a EFER, CR0 y CR4 usaban `options(nomem)`: el compilador podía reordenar accesos a memoria alrededor de cambios de protección (NXE, WP, SMEP/SMAP). | Se quita `nomem` en las escrituras (barrera de compilador). |
| A6 | Arranque | El editor de Limine permitía modificar la entrada de arranque y no se verificaba la integridad del núcleo ni de la configuración. | Hash BLAKE2b del núcleo en `path`, hash de la config inscrito en los cargadores BIOS y UEFI (incluida la imagen FAT del CD), editor desactivado. Verificado en QEMU: núcleo o config alterados → no arranca. |

## Hallazgos de severidad media

| ID | Problema | Corrección |
|----|----------|------------|
| M1 | CI en rojo: deriva de `rustfmt` y prueba de TLB con expectativa incorrecta. | Formato aplicado; la máscara pendiente ahora excluye CPUs que ya confirmaron. |
| M2 | `rollback` sin tablas creadas devolvía `RollbackFailed` si la invalidación fallaba, ocultando la causa real, y emitía un broadcast innecesario. | Retorno temprano con la causa real. |
| M3 | Handles de capacidad intercambiables entre tablas del mismo tipo (todas empiezan en generación 1): riesgo de *confused deputy* entre tareas. | Identificador de tabla dentro del handle. |
| M4 | Puerto serie: sin COM1 (o bus flotante que lee 0x00) el bucle de transmisión colgaba el arranque. | Sonda de loopback y espera acotada; salida *best effort*. |
| M5 | RDRAND/RDSEED aceptaban muestras atascadas (fallo conocido de AMD: todo unos con CF=1). | Se rechazan `0` y `u64::MAX`. |
| M6 | El PMM quedaba en estado parcial si el mapa de memoria era inválido a mitad de camino. | Validación completa antes de mutar estado. |
| M7 | Mapeos de usuario en la página 0 permitidos (explotación de NULL deref). | `NullPageUserMapping`. |
| M8 | `HhdmOffset` aceptaba desplazamientos no alineados o en la mitad baja. | Solo mitad alta y alineado a página. |
| M9 | Cadena de suministro del CI: acciones por etiqueta mutable, credenciales persistidas, toolchain `stable` flotante. | Acciones fijadas a SHA, `persist-credentials: false`, Rust 1.97.0 fijado, lockfile del fuzzer versionado. |

## Mejoras y hallazgos menores

- Verificación de paginación de 4 niveles: si CR4.LA57 está activo se aborta (todo el VMM asume 48 bits).
- `enable_boot_hardening` pasa a `unsafe fn` con contrato documentado.
- `PageTableFrame::physical_address` consumía el token de propiedad (imposible liberarlo después); ahora toma `&self` y el tipo es `#[must_use]`.
- CPUID de entropía se ejecuta una sola vez (CPUID provoca VM exits).
- El panic handler imprime archivo, línea y mensaje.
- El binario del núcleo se marca `test = false`; `clippy --all-targets` ya funciona.
- La prueba de arranque verifica todos los hitos, falla ante cualquier reporte de error del núcleo y añade una corrida `-cpu max` que cubre SMEP/SMAP/UMIP.
- El fuzzer cubre todos los tipos de región de Limine y rangos de núcleo arbitrarios, con invariantes de contabilidad, frame 0, doble liberación y reserva del núcleo.

## Riesgos abiertos (no corregibles en esta fase)

- **Secure Boot:** la verificación de la config inscrita solo es fuerte con UEFI Secure Boot y binarios firmados; sin ello un atacante con escritura al disco puede sustituir el cargador.
- **`SyscallPolicy` es `Copy`** y cualquier código con `&mut` puede reasignarla: la monotonicidad depende de que la política viva en estado privado del núcleo.
- **No hay IDT/GDT/TSS:** cualquier excepción produce un triple fault silencioso. Es la siguiente prioridad.
- **Marcos de datos sin poner a cero:** el PMM no limpia marcos; el futuro asignador de memoria de usuario debe hacerlo para evitar fugas entre procesos.
- **Toolchains nightly sin fijar** en Miri y fuzz (necesario para esas herramientas).

## Cinco críticos

- **Pesimista:** no se pudo compilar el núcleo para `x86_64-unknown-none` en el entorno de la auditoría; la validación del núcleo real depende del CI. La cadena de arranque se probó con un núcleo de prueba en C con el mismo linker script.
- **De la raíz:** la mayoría de los fallos venían de invariantes expresadas solo en comentarios (W^X, rango del núcleo, semántica de errores). Ahora están en el sistema de tipos o se verifican en tiempo de ejecución.
- **Optimista:** la base es sólida: `unsafe` acotado, Kani, Miri y fuzzing ya existían; las correcciones encajan sin rediseños.
- **Desconocido:** no hay modelo de amenazas escrito; las prioridades de seguridad futuras dependen de definir el atacante (físico, local sin privilegios, remoto).
- **Práctico:** siguiente paso: IDT/GDT/TSS con pilas IST para doble fallo, luego un modelo de amenazas breve.

**Veredicto:** apto para fusionar. CI en verde tras las correcciones: núcleo (fmt, Clippy, pruebas, ISO, arranque BIOS, BIOS `-cpu max` y UEFI), Miri, Kani y fuzz.
